# ADR 0003: Time-weighted metrics and LibreView CSV import

- **Status:** accepted
- **Date:** 2026-11-06
- **Milestone:** v0.4 (see [roadmap](../roadmap.md#v04-libreview-csv-import-and-defensible-analytics))

## Context

`get_glucose_stats` reports only sample statistics: every reading counts once, whatever span it represents. A graph with irregular samples, or one mixing 15-minute graph points with minute-by-minute current readings, is summarized as if each sample stood for the same time. For that reason `time_in_range_percent` and `gmi_percent` are always `null` today.

The local store from v0.3 ([ADR 0002](0002-local-store-and-collector.md)) holds history only from the time a collector started. A LibreView CSV export can fill in older periods without contacting the LibreLinkUp API. It also keeps history useful if the v4 API is retired (see [API retirement risk](../roadmap.md#api-retirement-risk)).

v0.4 adds time-weighted metrics, following the [international consensus on CGM time in range](https://pmc.ncbi.nlm.nih.gov/articles/PMC6973648/), and an offline `import-csv` command.

## Decision

### Time-weighted metrics

#### Durations

- Each sample's duration runs to the next sample, capped at 15 minutes: `min(time to next sample, 15 min)`.
- The last sample runs to `min(window end, sample time + 15 min)`.
- Time beyond the cap is uncovered. It is never attributed to a reading, so a long gap is neither bridged nor counted as zero.
- `coverage_percent` = covered duration / window duration.

#### Bands

- The consensus bands are fixed: `<54`, `54–69`, `70–180`, `181–250`, and `>250` mg/dL.
- Time in the user's configured target range is reported separately from the consensus bands.

#### Statistics

- The time-weighted mean, SD, and CV are reported next to the existing sample statistics. The sample statistics stay and keep their "sample" labels.
- `time_in_range_percent`, `null` today, becomes the time-weighted consensus 70–180 value.

#### GMI

- GMI % = 3.31 + 0.02392 × the time-weighted mean in mg/dL.
- It is reported only when the window is at least 14 days **and** coverage is at least 70%. Otherwise `gmi_percent` is `null`, with a reason.
- It is labeled an estimate, with no interpretation, and cites the consensus paper above.

#### One implementation

- The live and store paths share the same metrics code.

### CSV import

```sh
librelink-mcp-rs import-csv <file> --timezone <IANA> [--date-format mdy|dmy] [--db <path>]
```

#### Columns read

- Columns are located by header name.
- Only these are read: the device timestamp, the record type, and the historic and scan glucose columns.
- These are never read into memory beyond parsing, stored, or logged:
  - the "Generated by" name line
  - the serial number
  - insulin, carbs, and notes
  - ketone and strip values

#### Record types and units

- Record type 0 becomes origin `libreview_csv_historic`, and type 1 becomes `libreview_csv_scan`. All other record types are ignored.
- mg/dL or mmol/L is decided by the header. mmol/L values are multiplied by 18.0182 and rounded to 0.1 mg/dL.

#### Timestamps

- Device timestamps are local time with no offset, so `--timezone` is required. The zone is resolved with `chrono-tz`.
- Local times that are ambiguous or nonexistent because of a DST change are skipped and counted. They are never guessed.
- Date order is detected from the data. If the order is ambiguous and `--date-format` is not given, the import refuses with a clear message.
- `time_basis` is `csv_local_declared_timezone`.
- The `factory_timestamp` key is `"csv:"` + the original timestamp text. CSV rows therefore deduplicate among themselves through the existing primary key.

#### Patient

- Rows attach to the database's collector `patient_key`.
- If the database has none, the import refuses with "run collect at least once first".

#### Overlap with collected data

- Overlap is resolved when the data is read, not when it is imported: a CSV row within ±90 seconds of a non-CSV reading is dropped from query results.
- This works regardless of import order.

#### Output and the source file

- Output is counts only: imported, duplicate, and skipped by reason.
- The source file is never copied or modified.
- Files larger than 50 MiB are refused.

#### No lock

- `import-csv` takes no lock and does not refuse while a collector holds the database lock.
- An import is a write like the collector's, to the same database, and WAL mode handles a concurrent collector.
- The lock exists to keep two collectors from polling Abbott for the same database. An import makes no upstream request, so it is not that kind of writer.

### Plan

1. **Metrics module, wired into stats.** Durations, coverage, the consensus and target bands, time-weighted mean, SD, and CV, and GMI with its gate, used by both the live and store paths. Synthetic tests cover irregular samples, the 15-minute cap, the last sample, and the 14-day and 70% boundaries.
2. **CSV parser and `import-csv`.** The parser, the import command, and its refusals, tested on synthetic fixtures only.
3. **Overlap, docs, release, live check.** The ±90-second rule at read time, the docs, and the release. The PM then checks the import with a real export: only the PM inspects its header row, and the real file never enters the repo.

## Consequences

- `time_in_range_percent` changes from always `null` to a time-weighted value. This changes tool output and goes in the CHANGELOG.
- On the live path the graph covers about 12 hours, so `gmi_percent` stays `null` there in practice. A useful GMI needs the store or imported history.
- A new dependency, `chrono-tz`, embeds the IANA time zone database. That adds binary size, and its MSRV must stay within Rust 1.89.
- The database can now hold readings from before the collector started, from a file the user chose. The import cannot verify that the file belongs to the same person as the collected patient.
- The new origins and time basis add values to existing columns. The schema is unchanged.

## Open questions

These are concerns about the fixed decisions, for the PM to settle before or during the step they affect. None is a redesign.

1. **Retention deletes imported history.** `prune` removes readings older than the retention window by `COALESCE(observed_at_utc, first_seen_utc)`. Readings older than the window would be deleted at the next collector start, or within 24 hours. With the default 90 days, importing a year-old export would keep only the last 90 days. Options:
   - document it;
   - have `import-csv` refuse or warn about rows outside retention;
   - exempt CSV origins from pruning.

   Step 2 needs an answer.
2. **A historic reading and a scan in the same minute collide.** The key is `"csv:"` + the timestamp text, and LibreView timestamps have minute resolution. A type 0 and a type 1 row at the same minute share a key, so the second is counted as a duplicate and dropped. Including the record type in the key (for example `csv:0:` / `csv:1:`) would keep both. Two scans in the same minute would still collide, which seems acceptable.
3. **A 0.3.0 binary cannot read an imported database.** 0.3.0 treats an unknown `origin` as an error. After an import, a 0.3.0 `serve` would fail on store reads, and a 0.3.0 collector would keep writing. Bumping `user_version` to 3 (an empty migration) would make 0.3.0 refuse the database cleanly at open, which is the existing newer-version refusal, at the cost of no downgrade path.
4. **A long import can starve the collector.** The busy timeout is 5 seconds, and the collector exits with status 1 when a write fails. A single large import transaction could hold the write lock longer than 5 seconds. Proposal: insert in batches of about 1,000 rows per transaction.
5. **Band edges for fractional values.** Values are stored as reals, and mmol/L conversion produces tenths. Proposal: `<54`, `54 ≤ v < 70`, `70 ≤ v ≤ 180`, `180 < v ≤ 250`, `>250`, so a value such as 69.5 lands in exactly one band. The integer labels stay as in the consensus.
6. **Window edges.** Proposal: only samples inside the window count, a sample's duration is clipped to the window end, and the time from the window start to the first sample is uncovered. Also proposed:
   - SD is the duration-weighted population SD, with no Bessel correction.
   - Samples without a usable UTC time are excluded from the time-weighted figures and counted.
7. **Which coverage is gated.** Proposal: GMI is gated on the requested window, `days ≥ 14`, and on `coverage_percent` over that window, not on the observed span. Where `coverage_percent` sits in the reply, next to or inside the existing `coverage` object, is also open.
8. **Header language and number format.** LibreView exports use localized header names, and some locales write decimal commas or semicolon delimiters. Proposal for step 2:
   - support the English headers;
   - refuse any other header with a message naming the expected columns;
   - accept comma or semicolon delimiters only when that is unambiguous.

   A sample header from the PM's real export would help, inspected by the PM only.
9. **Date-order detection.** Proposal: if any day field is greater than 12, the order is decided. If every row could be either order, the import refuses unless `--date-format` is given. Whether exports can use a 12-hour clock with AM/PM is unknown and needs a synthetic fixture once the format is confirmed.
10. **Gaps and coverage for imported periods.** The v0.3 gap causes come from poll records, and imported periods have none, so their gaps would be labeled `before_collection`. Open:
    - whether CSV historic readings count as graph-like for the cadence estimate;
    - whether imported periods need their own gap label.

    This affects step 3.
11. **Skip reasons.** Proposed counted reasons:
    - unsupported record type;
    - unparsable timestamp;
    - DST-ambiguous;
    - DST-nonexistent;
    - missing or unparsable glucose value.

    Values are counted by reason only, never echoed.
12. **Size check.** Proposal: check the file size before reading, and also stop reading past 50 MiB, so a file that grows or a non-regular file cannot get past the limit.
13. **Device clock and travel.** One declared time zone cannot correct a device clock that was wrong or a period spent in another zone. The docs should say so, and the import cannot detect it.
14. **Clearing during an import.** `clear-local-data` refuses only while the collector lock is held. Because imports take no lock, a clear during an import is not refused. Imports are short, so documenting this may be enough.
