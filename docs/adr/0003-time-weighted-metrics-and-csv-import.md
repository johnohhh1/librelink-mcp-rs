# ADR 0003: Time-weighted metrics and LibreView CSV import

- **Status:** accepted
- **Date:** 2026-11-06 (open questions settled the same day)
- **Milestone:** v0.4 (see [roadmap](../roadmap.md#v04-libreview-csv-import-and-defensible-analytics))

## Context

`get_glucose_stats` reports only sample statistics: every reading counts once, whatever span it represents. A graph with irregular samples, or one mixing 15-minute graph points with minute-by-minute current readings, is summarized as if each sample stood for the same time. For that reason `time_in_range_percent` and `gmi_percent` are always `null` today.

The local store from v0.3 ([ADR 0002](0002-local-store-and-collector.md)) holds history only from the time a collector started. A LibreView CSV export can fill in older periods without contacting the LibreLinkUp API. It also keeps history useful if the v4 API is retired (see [API retirement risk](../roadmap.md#api-retirement-risk)).

v0.4 adds time-weighted metrics, following the [international consensus on CGM time in range](https://pmc.ncbi.nlm.nih.gov/articles/PMC6973648/), and an offline `import-csv` command.

## Decision

### Time-weighted metrics

#### Samples and the window

- The metrics take `(observed_at_utc, value)` samples and a window `[from, to]`.
- Only samples inside the window count.
- Samples without a usable UTC time are excluded from the time-weighted figures and counted.
- The time from the window start to the first sample is uncovered.

#### Durations

- Each sample's duration runs to the next sample, capped at 15 minutes: `min(time to next sample, 15 min)`.
- The last sample runs to `min(window end, sample time + 15 min)`.
- Time beyond the cap is uncovered. It is never attributed to a reading, so a long gap is neither bridged nor counted as zero.
- `coverage_percent` = covered duration / window duration.

#### Bands

The consensus bands are fixed, with exact edges, so every value falls in exactly one band:

| Band | Range (mg/dL) |
| --- | --- |
| very low | `v < 54` |
| low | `54 ≤ v < 70` |
| target | `70 ≤ v ≤ 180` |
| high | `180 < v ≤ 250` |
| very high | `v > 250` |

Time in the user's configured target range is reported separately from these bands.

#### Statistics

- The time-weighted mean, SD, and CV are reported next to the existing sample statistics.
  - The SD is the duration-weighted population SD, with no Bessel correction.
  - The sample statistics stay and keep their "sample" labels.
- `time_in_range_percent`, `null` today, becomes the time-weighted consensus 70–180 value.

#### GMI

- GMI % = 3.31 + 0.02392 × the time-weighted mean in mg/dL.
- It is reported only when the **requested** window is at least 14 days **and** `coverage_percent` over that window is at least 70%.
- Otherwise `gmi_percent` is `null`, with the reason code `window_too_short` or `coverage_too_low`.
- It is labeled an estimate, with no interpretation, and cites the consensus paper above.

#### One implementation

- The live and store paths share the same code, in `src/metrics.rs`.

### CSV import

```sh
librelink-mcp-rs import-csv <file> --timezone <IANA> [--date-format mdy|dmy] [--db <path>]
```

#### Columns read

- Columns are located by header name. English headers are supported. Any other header is refused with a message naming the expected columns.
- The delimiter is a comma, as in the export the PM inspected. A semicolon-delimited file has no matching header and is refused with the same message.
- Only these are read: the device timestamp, the record type, and the historic and scan glucose columns.
- These are never read into memory beyond parsing, stored, or logged:
  - the "Generated by" name line
  - the serial number
  - insulin, carbs, and notes
  - ketone and strip values

#### Record types and units

- Record type 0 becomes origin `libreview_csv_historic`, and type 1 becomes `libreview_csv_scan`. All other record types are ignored.
- mg/dL or mmol/L is decided by the header. mmol/L values are multiplied by 18.0182 and rounded to 0.1 mg/dL.

#### Timestamps

- Device timestamps are local time with no offset, so `--timezone` is required. The zone is resolved with `chrono-tz`.
- Local times that are ambiguous or nonexistent because of a DST change are skipped and counted. They are never guessed.
- Date order is detected from the data: if any day field is greater than 12, the order is settled. If every row could be either order and `--date-format` is not given, the import refuses with a clear message.
- `time_basis` is `csv_local_declared_timezone`.
- One declared zone cannot correct a wrong device clock or a period spent in another zone. The docs say so, because the import cannot detect it.

#### The dedup key

- The `factory_timestamp` column holds each reading's dedup key text:
  - for API rows, the factory clock text;
  - for imports, `csv:<type>:<ts>`, for example `csv:0:<ts>` or `csv:1:<ts>`, where `<ts>` is the original timestamp text.
- Including the record type keeps a historic reading and a scan in the same minute apart. CSV rows deduplicate among themselves through the existing primary key.

#### Patient

- Rows attach to the database's collector `patient_key`.
- If the database has none, the import refuses with "run collect at least once first".
- The import cannot verify that the file belongs to the same person as the collected patient.

#### Retention

Retention applies to every row; it is the user's privacy control.

- The collector records its `retention_days` in the `meta` table at startup. The default is 90.
- `import-csv` reads that value, or 90 if it is absent, and skips rows older than it, counted as `outside_retention`.
- The output then says that keeping longer history requires running `collect` with a larger `--retention-days`.

#### Overlap with collected data

- Overlap is resolved when the data is read, not when it is imported: a CSV row within ±90 seconds of a non-CSV reading is dropped from query results.
- This works regardless of import order.

#### Output and the source file

- Output is counts only: imported, duplicate, and skipped by reason. The reasons are:
  - unsupported record type;
  - unparsable timestamp;
  - DST-ambiguous;
  - DST-nonexistent;
  - missing or unparsable glucose value;
  - more than 5 minutes in the future (`future_time`);
  - `outside_retention`.

  Values are never echoed.
- The source file is never copied or modified.
- Files larger than 50 MiB are refused. The size is checked before reading, and reading also stops at 50 MiB, so a file that grows or a non-regular file cannot get past the limit.

#### Locks

- `import-csv` holds an exclusive lock on `<db>.import.lock`, not the collector's `<db>.lock`.
  - It runs alongside a collector; WAL mode handles the concurrent writes.
  - A second import on the same database is refused.
- `clear-local-data` refuses while either lock is held.

#### Writes and the schema version

- The import writes in transactions of about 1,000 rows, so it never holds the write lock long enough to exceed the collector's 5-second busy timeout.
- Step 2 bumps `user_version` to 3, with an empty migration. A 0.3.0 binary then refuses the database at open with its existing newer-version message, instead of failing on the unknown `origin` values. This removes the downgrade path, and the CHANGELOG says so.

### Plan

1. **Metrics module, wired into stats.** `src/metrics.rs`, used by `get_glucose_stats` on both the live and store paths, next to the unchanged sample statistics. Trends are unchanged in this step. Synthetic tests with a fixed clock cover:
   - irregular samples and the 15-minute cap;
   - the band edges;
   - the 14-day and 70% GMI boundaries;
   - empty windows.
2. **CSV parser and `import-csv`.** The parser, the import command, its locks, its refusals, the retention skip, and the `user_version` bump, tested on synthetic fixtures only.
3. **Overlap, docs, release, live check.**
   - The ±90-second rule at read time.
   - Gap handling for imported periods.
   - The docs and the release.
   - A PM check with a real export. Only the PM inspects its header row, and the real file never enters the repo.

## Consequences

- `time_in_range_percent` changes from always `null` to a time-weighted value. This changes tool output and goes in the CHANGELOG.
- On the live path the graph covers about 12 hours, so `gmi_percent` stays `null` there in practice. A useful GMI needs the store or imported history.
- A new dependency, `chrono-tz`, embeds the IANA time zone database. That adds binary size, and its MSRV must stay within Rust 1.89.
- The database can now hold readings from before the collector started, from a file the user chose, still bounded by retention.
- The new origins and time basis add values to existing columns. The schema version moves to 3, and 0.3.0 can no longer open the database.

## Settled questions

The step 0 review raised these concerns, and the PM settled them on 2026-11-06. The answers are recorded in the decisions above.

1. **Retention and imported history:** retention applies to imports. Rows outside it are skipped and counted.
2. **Historic and scan readings in the same minute:** the record type is part of the key.
3. **0.3.0 reading an imported database:** `user_version` becomes 3.
4. **A long import starving the collector:** the import writes in transactions of about 1,000 rows.
5. **Band edges, window edges, the population SD, the GMI gate, headers and delimiters, date order, skip reasons, and the size check:** the step 0 proposals were adopted.
6. **Clearing during an import:** an import lock, which `clear-local-data` respects.

Gap labels for imported periods, including whether CSV historic readings count toward the cadence estimate, remain to be decided in step 3.
